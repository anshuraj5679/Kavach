# Kavach: an AI data-leak guardian for campus portals

*Kavach* (कवच) means **shield**. It is an armour layer that sits in front of a college portal as middleware, inspects **every request in and every record out**, stops data leaks, and explains what happened in plain language.

Built for a web-security hackathon (Track 2 · Mission Portal Shield). It has three parts plus an attack simulator:

| Part | Where | What it is |
|---|---|---|
| Fake campus portal | `http://127.0.0.1:8000` | "Northfield Institute of Technology & Management": a **fictional** college with 1,000 Faker-generated students and five deliberate, labelled weak spots |
| Kavach agent | `agent/` | FastAPI/Starlette middleware: inspector → scanner → detector → actions → ledger → explainer |
| Security dashboard | `http://127.0.0.1:8000/admin` | Live threat feed, incidents, leak ledger, AI reports, and the big **Agent ON / OFF** switch |
| Attack simulator | `attacks/simulate.py` | Runs seven attacks, **localhost only** |

> **Fake data only. Fictional college. Localhost only.** Every name, USN, phone, Aadhaar-style number, address, mark and fee record is generated by Faker from a fixed seed. The portal is deliberately vulnerable for teaching. It binds to `127.0.0.1`, and the simulator refuses any other target.

## Setup

Requires Python 3.11+.

```bash
pip install -r requirements.txt
python run.py
```

* Portal: <http://127.0.0.1:8000>
* Dashboard: <http://127.0.0.1:8000/admin> (served to localhost only)

Helpers:

```bash
python run.py --accounts   # print demo logins
python run.py --reseed     # rebuild the fake database (same seed → same people)
python run.py --reset      # clear the Kavach ledger before starting
```

### Optional: AI-written reports

Reports work **offline** with a built-in template. To have an LLM write them, set one key before `python run.py`:

```bash
export ANTHROPIC_API_KEY=...          # Claude (default model: claude-opus-5-5)
# or
export OPENAI_API_KEY=...             # requires: pip install openai
export LLM_MODEL=...                  # optional model override
```

On Windows PowerShell use `$env:ANTHROPIC_API_KEY = "..."`. The dashboard header shows which writer is active, and every report says `written by: llm` or `written by: template`.

## The 3-minute demo script

**Setup (before you present):** `python run.py` in one terminal, the dashboard open on the projector, a second terminal ready.

**0:00 · The portal.** Open <http://127.0.0.1:8000>. "This is a typical college portal: results, library, fees, admissions." Point at the ribbon: fictional college, fake data. Log in as 101 (`05032004`, `NITM240101`) and show the results page. Point at the URL: `/results`.

**0:30 · Agent OFF.** On the dashboard, flip the switch to **OFF**. The header turns red and the banner reads *"Agent is OFF: requests go straight to the database."* Run:

```bash
python attacks/simulate.py all
```

Read the red lines out loud: **300** students' results scraped, **420** library borrowers' phone, Aadhaar and address exposed, **1,000** applicants dumped by SQL injection, **20** other students' fee receipts read (including plain-text passwords), the real Priya **locked out of her own account**, Kavya's password cracked, and a hijacked session. Then turn to the dashboard: **it shows nothing.** "That is today's reality: the college never finds out."

**1:15 · Agent ON.** Flip the switch to **ON** (the colour turns green). Run the same command:

```bash
python attacks/simulate.py all
```

Watch the dashboard fill in live:

* **Scraping**: the first changed `?roll=` is refused. **No marks get out**, the attempt is recorded, and the student whose record was targeted is told. Rahul's own pages keep working.
* **Over-exposure**: phone, Aadhaar and address **masked in flight**; the 420-row dump **stopped**.
* **SQL injection**: blocked **before the database was touched**.
* **Receipt IDOR**: refused on the first try, and every try after it.
* **Lockout attack**: the attacker is blocked after 5 tries, before the portal's own 10-try lock. **The real Priya still logs in.** A classmate on the same Wi-Fi IP, on her own device, logs in fine too.
* **Password guessing**: blocked after 5 guesses.
* **Session hijack**: a cookie replayed from another device is rejected.

**2:15 · Explain.** Click the *IDOR blocked* incident. The AI report covers what happened, why it was flagged, the exact impact, the action taken, and **the root-cause code fix** pointing at `WEAK SPOT #1` in `app/portal.py`. Scroll to the **leak ledger**: whose record, which fields, to whom, from which IP, and when.

**2:45 · Close.** "Rules decide, the AI explains. Kavach doesn't replace fixing the portal: it buys the college time, tells them exactly what to fix, and tells students the truth."

Shortcut for rehearsal: `python attacks/simulate.py all --compare` runs everything with the agent OFF and then ON, and prints a side-by-side table.

## How Kavach works

```
request → inspector → (portal + DB) → scanner → detector → actions → ledger → dashboard
                                                                       ↘ explainer (LLM or template)
```

| Stage | File | Does |
|---|---|---|
| Gateway | `agent/gateway.py` | Starlette middleware that every request and response passes through; issues the device-ID cookie |
| Inspector | `agent/inspector.py` | SQL-injection patterns (before the DB), ownership mismatch (`?roll=` / `?userId=` ≠ session), session guard, `client_ip()` |
| Scanner | `agent/scanner.py` | Splits outgoing records into the viewer's own and other people's; finds PII **by field name and by value pattern** (10-digit phone, `xxxx xxxx xxxx` Aadhaar, email); masks other people's PII; strips passwords; counts rows for mass-dump detection |
| Detector | `agent/detector.py` | Sliding-window counters per IP + device + roll; risk score 0–100 with reasons and severity; optional IsolationForest anomaly score |
| Actions | `agent/actions.py` | Block IP + device, freeze account (OTP stub), end session, stop response, branded 403 page |
| Ledger | `agent/ledger.py` | Incidents, one row per leaked or masked record, live events, stats, blocks. SQLite-backed (`data/ledger.db`, survives restarts) with an in-memory cache |
| Explainer | `agent/explainer.py` | Admin report, student notice and severity, cached per incident version |
| Notifications | `agent/notify.py` | In-app alerts to the student (portal bell and Account page) and to the IT head (dashboard) |
| Config | `agent/config.py` | **Every threshold** and the palette tokens |

### Rules decide, the AI explains

Every allow, mask or block decision comes from the deterministic thresholds in `agent/config.py`:

| Setting | Default | Meaning |
|---|---|---|
| `OWNERSHIP_ZERO_TOLERANCE` | True | on **every page and API**: a link carrying another student's ID (`roll`, `usn`, `userId`, `student`, … in any case, even repeated) or another student's challan / receipt number is refused on the first try (and on every try after it), recorded, and the IT head and the record's owner are told, once per attacker and target. The device is not blocked, so the student's own pages keep working. Set False for the older rule below |
| `FOREIGN_RECORD_LIMIT` | 3 | (only when zero tolerance is off) other people's records an actor may see in the window before being blocked |
| `ROW_SPIKE_LIMIT` | 100 | other people's rows in one response that count as a mass dump (response stopped) |
| `FAILED_LOGIN_LIMIT` | 5 | wrong tries per IP + device (the portal's own lock is at 10) |
| `SHARED_IP_LOGIN_LIMIT` | 3 | tries for other devices on an IP that already has a blocked device |
| `IP_FAILED_LOGIN_CEILING` | 20 | all devices on one IP combined (catches attackers who drop cookies) |
| `WINDOW_SECONDS` | 300 | sliding window |

The anomaly model can raise an incident's risk score but never overrides a hard rule. The LLM receives only **structured facts** (counts, field *names*, record ids, timestamps, the root-cause mapping), never raw personal data, and it never sees a live request.

### The three personal-account protections

1. **Lockout shield: block the attacker, not the student.** Every browser gets a secret device-ID cookie. Failures are counted per **IP + device**, not per USN, and the attacker's device is blocked at 5 tries, before the portal's 10-try USN lock can trigger. On shared campus Wi-Fi: same device as the attacker → blocked; same IP, different device → allowed with fewer tries; different IP and device → normal. The student and the IT head are notified: *"Someone tried your account 5× from IP x. Kavach blocked that device. Your account is NOT locked."*
2. **Session-hijack guard.** Each session is bound to the device it was created on. The same cookie arriving from another device ends the session. A 10-minute idle timeout covers an abandoned lab PC (same device, same IP), and *Log out from all devices* is on the Account page.
3. **Forgotten login on someone else's phone.** A device the student has never confirmed is **untrusted**: the student is notified on first login, and the session ends after 3 idle minutes, after 15 minutes in total, or when the network (IP) changes. Each new-device alert has *"This wasn't me: log out everywhere"* and *"Trust this device"* actions.

### Availability shield (results day)

The problem statement says portals *"go down at the worst possible moment"* and *"lack someone watching them continuously"*. `agent/availability.py` handles both kinds of heavy traffic, and its own watchdog keeps an eye on the portal.

| Traffic | Example | What Kavach does (agent ON) |
|---|---|---|
| **Bad: a flood** | A few bot machines sending far more requests than any person | Refuses a source that goes over a speed limit, **or** keeps more than 8 requests open at once (a person's page has about 4), **or** takes more than 15% of all traffic while the portal is busy. Refused for 60 s with HTTP 429, at the door, before any inspection or database work, and its requests already waiting for the server are dropped. Each refusal is held for 3 s (a *tarpit*), so a bot that retries instantly sends about 20 requests/s instead of about 1,500. When the server is busy, logged-in students and the critical lane (login, fees, receipts) go to the front of its line, so bots that slip in before they are spotted cannot delay real students |
| **Good: a rush** | Results are published and hundreds of real students open them at once | **Never blocks anyone.** Switches **rush mode** on by itself: fee payment, receipts and login keep a reserved lane, results queue fairly (one place per student, however often they refresh, with a *"You're number N in line"* banner and automatic retry), library and admissions search are paused. Kavach also pauses its own optional anomaly model. Rush mode switches off when traffic is calm again |

**Portal health panel** (dashboard, under the totals): Up / Slow / Down, response time, requests per second, requests in progress, results queue, fee-lane speed and flood refusals, with a 3-minute chart in which rush mode is shaded. Response time measures real users: requests from sources marked as flooding are left out. Rush mode only switches on for a real crowd (at least 10 different sources), never for a few flooding machines. The IT head gets an alert when the portal turns Slow or Down, and each flood and rush gets an incident with a report.

**Demo: results-day server.** On a laptop the demo portal answers in 1 to 2 ms, so a few hundred students hardly strain it. The *Results-day server (demo)* switch in the panel (`app/capacity.py`, off by default) makes it behave like a real campus server: 8 workers and a database that takes about 100 ms per query. It simulates only the server; Kavach's lanes, queue and flood blocking are real. The simulator switches it on for its runs (`--real-server` to skip): the rush uses that mid-size server, and the flood uses a small, busy one (2 workers, 250 ms database), so the difference shows in a browser.

**Live demo in a browser:**

```bash
python attacks/simulate.py bots             # prints BOTS STARTED, keeps flooding until Ctrl+C (10 min at most)
```

With the bots running and the agent OFF, every page you open in the browser takes about 15 to 20 seconds. Switch the agent ON from the dashboard while the bots keep running, and pages open in about 0.3 seconds, however often you click. The terminal prints a status line every 5 seconds: bot requests served by the portal (agent OFF) or refused by Kavach (agent ON). Kavach counts each source's open requests even while the agent is OFF (bookkeeping only), so the bots are recognised by their very next request once it is switched ON. Their requests already waiting in the server's line are dropped, and logged-in students go to the front of the line. A logged-in student who keeps clicking refresh is never mistaken for a bot.

**Timed comparisons:**

```bash
python attacks/simulate.py rush --compare    # 300 students open results at once while Sneha pays her fees
python attacks/simulate.py flood --compare   # 4 bot machines flood the portal for 30 s while Sneha opens Results
```

Measured on the development laptop (numbers vary from run to run and machine to machine):

| | Agent OFF | Agent ON |
|---|---|---|
| Rush: fee payment, median (300 students) | about 7.5 to 8 s | about 0.25 s |
| Rush: first result, median | about 2.3 s | about 3.1 s (fair queue) |
| Flood: real student opening the whole Results page, median | about 16 to 17 s | about 0.29 s (the same as with no flood) |
| Flood: bot requests that got through (30 s flood) | about 250 | about 15 |
| Flood: portal health during the flood | Slow / Down | Up the whole time |

`flood` and `rush` are not part of `all`, so the 7-attack comparison above is unchanged. Limits: this protects the website itself. A very large real-world attack, from millions of machines, is stopped earlier by network services such as a CDN.

### Protected downloads (receipt and acknowledgement)

Two buttons download a PDF straight away: *Generate receipt* on **Fees** and *Download acknowledgement* on **Acknowledgement**. The Acknowledgement page sits between Admissions and Fees, and shows the student's odd-semester course registration (9 courses, 21 credits) with the declaration and signature lines. Both buttons carry `data-kavach-download` and are protected the same way.

* **Agent OFF:** each button is a plain link (`/api/fees/receipt/download?userId=…&challan=…`, `/api/acknowledgement/download?userId=…&sem=5`). Dragging it into another tab, or pasting it there, downloads the file in that tab too. These are weak spots #4b and #6.
* **Agent ON:** the real URL is never in the page. Each button points to a random dead end (`/kavach/scrambled/<id>`), and the guard script keeps the real URL in memory.
  * **Click:** the page gets a one-time ticket from `/kavach/ticket`, bound to the session, the download, the student and the document, and valid for 30 seconds. It then downloads with the ticket in an `X-Kavach-Ticket` header. The download starts at once.
  * **Drag a button out:** the drag carries only the dead-end URL. The dashboard shows a *"… link moved out of the … page"* incident, a feed line, and an IT-head alert when the link is dropped outside the window. The link is re-scrambled after every drag.
  * **Open the dragged link anywhere:** a Kavach page explains that the link was scrambled, nothing downloads, and the dashboard logs who opened it and from which IP.
  * **Paste or type the real URL in another tab:** refused, because a new tab cannot send the ticket header (*"… download refused … no valid tab ticket"*). A ticket for one document never opens another.
  * **Change `?userId=`** to another student: refused before the PDF is built (zero tolerance, like receipts).

### Extension guard

Every logged-in page loads `static/kavach-guard.js`, which reports extension footprints to `/kavach/extension`. The server keeps a **baseline** for each session:

* **Extensions already active at login are allowed.** The first logged-in page sets the baseline, and the dashboard notes them: *"Rahul Sharma (101) logged in with browser extension(s) already active: Leo Wallet, Shield Wallet. Allowed for this session."*
* **An extension connected after login logs the student out.** This covers an extension switched on, clicked into the page, or showing up on a later page. The student lands on the login page with an explanation, and the dashboard shows a *"Browser extension connected in the session of …"* incident, a feed line and an IT-head alert naming the extension where it can.
* A new generic page change (an extra element, a hooked function) while extensions were already active is logged as a warning, not a logout, because one of those extensions most likely caused it. A new extension id, custom element, marker attribute or foreign script always logs the student out.
* The baseline is taken on the first page after login **even while the agent is OFF**, and switching the agent ON never resets it. The guard checks in every 4 seconds and holds whatever it saw while the agent was OFF, so an extension opened during that time is caught as soon as the agent is switched ON, with no refresh and no new login.
* **Right-click extensions** read the selected text inside the browser and never touch the page, so no page can see them. While the agent is ON, the right-click menu (mouse, Shift+F10 and the menu key) is switched off on logged-in pages. The student sees a short notice, and the dashboard feed logs *"Right-click menu blocked for …"*.
* **Right-click unblockers** (Allow Right-Click and similar) swap the browser's `preventDefault` so that pages cannot cancel right-click, copy or selection. Kavach keeps its own copy of the original, so the right-click block keeps working. It also checks those built-ins (`MouseEvent`/`ClipboardEvent.preventDefault`, `Event.preventDefault`, `Selection.removeAllRanges`, `addEventListener`, `alert`) on every page change and every right-click. Any swap is tampering and logs the student out, **even if the unblocker was on before login**, because it disarms Kavach itself. A right-click menu that opens without ever reaching Kavach counts too.
* Browser features such as Chrome's *Save password?* bubble are not part of the page and are never seen.

A footprint is any of these:

* a file loaded from a `chrome-extension://` style URL
* a custom element such as `<grammarly-extension>` (the portal defines none)
* an element, style or iframe added outside `<main>`
* a marker attribute on `<html>` or `<body>`
* `fetch` or `XMLHttpRequest` replaced to intercept data

Limits: a web page cannot list installed extensions. Extensions that never touch the page are invisible, but they also cannot read it. The check runs in the browser, so a determined attacker can disable it: it protects students from extensions, it is not a defence against attackers. It is enforced only while the agent is ON. Set `EXTENSION_GUARD = False` in `agent/config.py` to turn it off. Helpful extensions such as password managers and Grammarly trigger it too.

> A website cannot read a MAC address. Kavach uses the device-ID cookie plus the IP.

> `client_ip()` reads `X-Forwarded-For` so the simulator can play several attackers from one machine. In production, trust that header **only** from your own reverse proxy.

## The deliberate weak spots

Each is marked `# WEAK SPOT` in the code, with a `# SAFE VERSION:` comment showing the fix.

| # | Where | Flaw | What Kavach does |
|---|---|---|---|
| 1 | `app/portal.py` → `api_results` | IDOR: `?roll=` is never checked against the session | zero tolerance: every foreign `?roll=` refused and recorded, owner notified; own pages keep working |
| 2 | `app/portal.py` → `api_library_borrowers` | `SELECT *` sends phone/Aadhaar/address the page never shows; no `?limit=` cap | masks PII in flight; stops dumps over 100 rows |
| 3 | `app/portal.py` → `api_admissions_search` | SQL built by string concatenation; raw DB errors echoed | blocks the pattern before the DB |
| 4 | `app/portal.py` → `api_fee_receipt` | IDOR on `?userId=`, plus `SELECT *` leaks Aadhaar and password | zero tolerance: every foreign `?userId=` refused and recorded, owner notified; own pages keep working |
| 4b | `app/portal.py` → `api_fee_receipt_download` | The *Generate receipt* PDF is a plain GET link that works in any tab or site it is dragged or pasted into | scrambles the link on the page, downloads only with a one-time tab ticket, logs drags and refused opens |
| 6 | `app/portal.py` → `api_acknowledgement_download` | Course acknowledgement PDF: student taken from `?userId=` (IDOR) and a plain GET link that works in any tab | refuses foreign acknowledgements, scrambles the link, downloads only with a one-time tab ticket |
| 5 | `app/auth.py`, `app/portal.py` | DOB passwords, ID-card number as "second factor", per-USN lockout, sessions never expire and aren't bound to a device | lockout shield, session guard, untrusted devices |

## Attack simulator

```bash
python attacks/simulate.py all                 # everything, against the current agent state
python attacks/simulate.py all --compare       # OFF then ON, side by side (leaves the agent ON)
python attacks/simulate.py scrape              # or: overexposure | sqli | receipt | lockout | bruteforce | hijack
python attacks/simulate.py sqli --target http://example.com   # → REFUSED
```

Each attack comes from its own fake attacker IP (`X-Forwarded-For`), so blocking one does not hide the next. `all` resets the ledger, blocks and portal lockouts first (`--no-reset` to skip). The host guard accepts only `127.0.0.1`, `localhost` or `::1`, and also checks that the name resolves to a loopback address.

## UI notes

* Two coordinated themes driven by CSS variables: light, institutional portal (`static/portal.css`) and dark SOC dashboard (`static/dashboard.css`).
* Motion with meaning: feed items slide in, stat tiles count up and pulse when they change, and the whole dashboard flips from green to red when the agent is switched off. All of it respects `prefers-reduced-motion`.
* Clear states: loading skeletons, empty states, a branded *Blocked by Kavach* page (never a stack trace), inline blocked cards in the portal, and a reconnecting indicator on the dashboard.
* Accessibility: labelled controls, visible focus rings, `role="switch"` toggle, `aria-live` threat feed, a modal report drawer with focus return and Esc to close, keyboard-navigable tabs, and severity always shown as text, never colour alone.
* Deep link to a report: `/admin#INC-0001`.
